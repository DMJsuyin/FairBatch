# FairBatch v0.3：技术机制与路演底稿

## 一句话产品价值

薄流动性市场里，交易者不希望同一组合理报价仅因进入区块的先后而得到不同结果。FairBatch 把报价收进固定窗口，封盘后按公开规则统一定价；用户只确认限价与数量，其余步骤可由任何代发者推进。

技术主线：**把排序工作交给开放求解器，把决定资产归属的验证与计算留在合约。**

## 1. 无需信任求解器的排序见证

求解器提交两个紧凑字节串：买方订单编号、卖方订单编号。每个编号占 1 字节，每轮最多 32 笔。它不能提交新的价格、数量、成交价或自选分配结果。

合约从已封盘的存储订单取数据，在 O(n) 中验证：

1. 编号在范围内，而且对应已揭示、非零数量的订单。
2. 方向与所在队列一致。
3. `seen & (1 << index) == 0`：同一订单不能重复。
4. 相邻报价满足价格优先、同价地址升序。
5. 最终 `seen == expected`：所有有效订单都出现，没有漏掉任何一笔。

完整性、唯一性、有序性都成立后，合约自行双指针扫描。错误见证整笔回滚，不会写入部分清算结果。任何钱包都可以调用 `settleWithWitness`；无可用求解器时仍可调用 `settle`，合约自己排序。没有白名单、中心化价格输入或挑战期。

“排序见证”只是可验证的执行提示，不是零知识证明，也不要求信任服务器。

## 2. 最大成交量、统一价与整数分配

令买单按限价降序，卖单按限价升序。在买价不低于卖价时，双指针取两端剩余数量的较小值。每一步至少耗尽一笔订单，扫描 O(n)。

为什么能达到最大成交量：优先消耗最高买价和最低卖价不会减少剩余订单的可匹配机会；当最高剩余买价已经低于最低剩余卖价时，任何剩余买卖组合都无法成交。因此终止时不能再增加成交量。

设最大成交量 V，第 V 手对应的边际卖价为 L、边际买价为 H。所有实际成交订单共同可接受 `[L,H]`，采用固定规则：

`P = L + floor((H-L)/2)`。

每侧先满足价格更优的档位。边际同价档的剩余可分配量为 R，总申报量 Q，第 i 单申报量 qᵢ：

`基础分配 fᵢ = floor(R*qᵢ/Q)`，`余数 rᵢ = (R*qᵢ) mod Q`。

剩余整手数给余数最大的订单，同余数按地址升序。合约对余数建最大堆，建堆 O(k)，补 e 手 O(e log k)，替换反复全表找最大余数。每单相对精确比例的舍入误差小于 1 lot；每侧成交总量都恰好是 V。含边际分配的见证清算最坏 O(n log n)，不是笼统的 O(n)。

这是标准机制的工程组合，不把最大余数法、哈希承诺或 EIP-712 宣称为原创算法。

## 3. 最小持久化账本

旧版清算为每单存三项：成交量、应收 base、应收 quote。后两项其实可由成交量、统一价和原始锁仓唯一算出。

新版清算只持久化成交量和轮次结果；`getOrders/getOrder` 返回实时推导的应收金额，`claimFor/claimMany` 用同一公式转账：

- 买单：base = `fill × BASE_LOT`；quote 退款 = `escrow − fill × P × QUOTE_UNIT`。
- 卖单：base 退款 = `escrow − fill × BASE_LOT`；quote = `fill × P × QUOTE_UNIT`。

由两侧成交量都等于 V，可得 base 与 quote 各自守恒。清算不做外部代币转账；领取先标记已领取、减少 liability，再转给原 owner。重复领取无效，代发者不能修改收款人。到期或未揭示退出依照原有规则返还锁仓；切换新轮次不会改变历史应收金额。

注意：不是把应收金额交给服务器算。**合约和浏览器都能独立计算，而代币实际转移仍由合约公式决定。**

## 4. 密码学承诺与 EIP-712 委托

### 密封订单

`commitment = keccak256(abi.encode(DOMAIN, chainId, contract, round, owner, isBuy, lots, ticks, salt))`

`DOMAIN = keccak256("FairBatch:v0.3")`，salt 由浏览器 CSPRNG 生成 32 字节。链上初始只提交承诺和锁仓，不上传明文限价、数量和 salt；揭示窗口才公布。哈希是承诺，不是可解密密文。

### 委托提交

EIP-712 domain = `{name: FairBatch, version: 0.3, chainId, verifyingContract}`。

签名结构 `CommitIntent(roundId, owner, isBuy, commitment, escrow, nonce, deadline)`。中继收到的仍然是密封承诺，无法从代发参数直接读取报价。

合约验证签名、截止时间、nonce 后，从 owner 的已授权代币余额锁仓。成功提交后 nonce 增加；直接提交也消耗 nonce；`invalidateNonce` 可撤销尚未执行的签名。域隔离阻止跨链、跨合约、跨协议版本复用。OpenZeppelin 的 ECDSA 校验处理非规范签名，SignatureChecker 支持 ERC-1271 合约钱包。

EIP-712 本身不提供重放保护，本项目显式实现 nonce、deadline 和轮次限制。签名代发转移的是提交 Gas 的支付者，不是让链上交易免费；首次代币授权仍是链上操作。

兼容性：项目 EVM 目标为 Shanghai，签名组件固定使用 `@openzeppelin/contracts-shanghai`（官方 contracts 5.0.2 的 npm alias），其他既有组件保持 5.6.1。5.6 的签名依赖使用 Cancun MCOPY，不能直接用于当前 Ganache Shanghai。

### 可选择的锁仓填充

揭示条件从“锁仓恰好等于订单需求”改为“锁仓不少于订单需求”。用户可勾选按 1/2/4/8…单位向上归档，例如需求 5.15 dUSDC 时锁 8 dUSDC。成交 5 dMON、统一价 1 时退回 3 dUSDC。

同一档位可以对应不同订单需求，因此锁仓金额不再精确暴露卖出数量或买入预算。方向、钱包、档位以及公开历史仍可见；不能称为全隐私暗池。填充有额外资金占用，默认由用户选择。

## 5. 双实现验证与现场攻防

链上：双指针求成交量 + 最大堆分配余数。

浏览器/测试参考：枚举离散报价求 `max(min(D(P),S(P)))` + 独立排序分配余数。两者不共用清算代码。已结算轮次的统一价、区间、总量、每单分配逐项核对。

`ClearingVerified` 事件携带结果指纹与求解器地址，供复算定位；哈希指纹本身不是正确性证明，正确性来自合约校验与参考复算。

可复现测试覆盖：

- 65 组随机订单，两套链上路径与独立参考算法比较；反转提交顺序后按 owner 比较逐笔分配。
- 32 笔上限、极大数值、价格优先、同价比例、最大余数和同余数决胜。
- 漏单、重复、错方向、越界、乱序、混入未揭示订单全部拒绝。
- 签名每个字段被修改、跨链/跨合约/跨版本、重放、nonce 撤销、过期签名、短签名拒绝。
- ERC-1271 钱包授权成功，代发后的退款仍归原钱包。
- 错误 salt、过早/过晚操作、抵押不足、填充超额退还、过期自救、重复领取与逐资产守恒。

## 6. 五分钟路演顺序

- **0:00–0:40 痛点**：同样三笔报价，连续撮合六种顺序得到不同价格和买方。
- **0:40–1:15 下单**：开启轮次，限价 1.03 买 5，选择锁仓填充，签名委托。展示公开锁仓 8，但订单内容在封盘前仍密封。
- **1:15–2:15 为什么公平**：用供需曲线讲 V、[L,H]、统一价；同价按量分配，不按谁先提交。等候封盘时解释状态流程。
- **2:15–3:15 真正结算**：自动揭示后任何求解器可提交排序。展示收到资产与退回多余锁仓，浏览器独立复算一致。
- **3:15–4:15 攻击演示**：点击“验证漏单攻击”，去掉一个有效订单编号，合约 `eth_call` 明确返回 `incomplete witness`。这是调用真实链上校验的只读实验，不伪造弹窗结果。
- **4:15–5:00 工程指标**：展示 `protocol-benchmark.json` 中完整结算与结算+领取数据，并说明基线与编译环境。落到“计算可外包，资金结果不能外包”这句话。

## 7. 评委可能追问

- **求解器故意漏单？** 位图完整性失败，整笔交易回滚。
- **求解器离线？** 换任意提交者，或 `settle` 链上独立排序；再超时可 `claimFor` 自救。
- **签名被偷走？** 只能代发原订单，不能改任何已签字段或收款人；执行后 nonce 消耗。
- **订单顺序完全没影响？** 对固定有效订单集合，清算与逐人分配与提交顺序无关。容量满时的准入、审查和选择性不揭示是不同问题。
- **不揭示会罚没吗？** 当前没有罚没，未揭示不成交并按规则退出。保证金参数需要博弈/成本分析，不能仅加一个罚款常数就声称抗所有操纵。
- **地址同余数决胜是否可被刷？** 可以磨地址/拆单；该规则保证确定性，不保证抗 Sybil。舍入误差按单小于一手，不能进一步宣称总体抗拆单。
- **为什么适合 Monad？** 可部署 EVM，分市场/分轮次可减少跨市场依赖；当前单市场仍有共享状态。不将本地 Gas 数据包装成 Monad 并行 TPS。

## 实测成本（本次本地回归）

同一组 32 笔逆价格顺序报价，receipt 实测，Shanghai / solc 0.8.30 / viaIR / optimizer 200：

| 阶段 | v0.2 | v0.3 见证清算 | 变化 |
| --- | ---: | ---: | ---: |
| 完整 settle | 2,566,288 | 1,237,340 | 降低 51.78% |
| claimMany 全部领取 | 934,863 | 943,401 | 按需计算略增加 |
| settle + claimMany | 3,501,151 | 2,180,741 | 降低 37.71% |

纯计算的六组 8/16/32 笔、逆序/同价分配样本均保存在 JSON 中；小批量同价组可能因验证与堆管理开销而更贵，不宣称所有输入都更快。以上合计不包括提交、授权和揭示成本，签名委托也不会免除链上验证成本。
